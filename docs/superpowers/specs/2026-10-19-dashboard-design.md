# FTC Knowledge Bank Dashboard 设计

日期：2026-10-19。状态：用户已于 2026-10-19 批准完整方案；本文件描述已批准的目标行为，不代表功能已完成。

## 目标

提供中文本地管理台，实时查看和修改规则，解释规则的来源、策略层级和适用范围，追踪调用实际经过哪些检测及被什么拦截。复用现有确定性引擎，不在前端重新实现规则优先级。

当前代码检查：已有 `serve` 聊天页面与 token 保护的 localhost HTTP API；其启动需要模型配置。`validate`、`resolve`、`check` 是独立 CLI 调用，目前没有统一持久化审计。内置编辑 Agent 有路径、引用及分支等保护，但当前编辑写入路径没有调用 Standardizer，不能将现有编辑成功描述为已通过规则 diff 检测。2026-10-19 运行现有 CLI 的 `validate knowledge --json` 返回 `ok:true`、48 条规则。

## 方案比较与推荐

1. 推荐：新增独立 `ftckb dashboard --knowledge PATH`，复用当前 Kotlin HTTP 服务模式、规则加载器、resolver 和 Standardizer；不需要模型 API key。静态 HTML/CSS/JS 与本地 API 同源。
2. 扩展 `serve` 聊天页：复用入口最多，但规则管理被模型配置和聊天状态绑住，不适合作为常用管理台。
3. 独立前端工程和后台：便于未来多人部署，但新增运行环境、构建链与权限体系，本轮无实际需要。

## 界面与交互

采用浅灰蓝背景、深蓝导航、白色数据面板；蓝色表示选中，绿色表示检查通过，琥珀色表示需要复核，红色表示拦截。颜色始终配文字。主体使用系统中文字体，ID、时间和路径使用等宽字体。核心视觉是调用详情中的检测阶段轨迹，每阶段显示实际状态及原因。

顶部显示当前知识库、刷新时间和连接状态。导航包含概览、规则管理、归属与裁决、调用审计。桌面采用列表与详情并列，窄屏切为单列；支持键盘焦点、明确标签和减少动态效果。静态资源本地提供。

### 规则管理

- 列出所有规则，支持搜索 ID、标题和正文，以及按状态、authority、policyLevel、team、season、profile、硬检查/条件式 soft/无条件 soft 筛选。
- 详情展示 instruction、rationale、evidence、approval、checks、reviewTriggers、示例和源文件。来源 authority、策略 policyLevel、适用范围独立显示，不能用文件夹或 ID 前缀代替。
- 提供新增候选规则、编辑、修改适用范围、候选批准/拒绝。归属调整通过合法字段表达，并展示与文件组织的关系。首版不提供批量删除或重写全部文件。
- 批准操作复用 ApprovalPolicy，要求明确批准人、角色及适用队伍；当前策略是角色声明校验，界面不声称已通过身份认证。
- 修改已批准规则的实质内容或归属时，清除旧 approval 并转为 candidate，要求重新批准；ID 不可在普通编辑中更名。
- 编辑遵循“编辑 → 查看差异与校验结果 → 保存”。在临时副本中对完整知识库执行校验；有上下文时同时预览裁决影响及冲突。错误显示到规则及字段。
- 保存使用文件内容摘要防止覆盖外部修改，拒绝越界路径和 symlink，原子替换单个目标文件，保留其他规则与注释，写入修改审计。失败保留原文件。不会自动 commit/push。

### 归属与裁决

用户显式输入 team、season，并选择 generic 或命名 profile；未选完整上下文仍可看规则目录，不显示猜测的生效数量。normal 是默认模式，test/dev 仅由用户显式选择，不保存为项目默认。

调用现有 RuleResolver，逐条显示 active、excluded 及原因、overridden 及 winner IDs、conflict 及同层级候选。展示 OFFICIAL > GLOBAL > LOCAL > SHARED，并解释 official 由来源取得最高优先级。首版提供单个上下文的裁决浏览，不做多项目资产管理。

### 调用审计

- 持久化记录新版 CLI 的 validate/resolve/check、chat/serve 的用户请求和编辑事务；dashboard 的规则修改、批准和手动检测也记录。普通轮询读取不计入检测覆盖率。
- 每条记录包含唯一调用 ID、开始与结束时间、入口、命令、知识库及版本摘要、可用的上下文、耗时、退出码、运行状态、各检测阶段状态、命中规则、位置及原因。
- 生命周期区分 started/completed/failed；每阶段区分未执行、通过、阻止及不适用。进程中断留下未完成记录，不能当作通过。
- `resolve` 成功只表示裁决成功，不表示 diff 已检查。`check` 的知识校验、裁决、diff 读取与 Standardizer 阶段分别记录；参数错误和知识冲突保留实际失败阶段。
- 明确区分硬违规、soft 待复核、dev 降级提醒、参数错误、知识无效、同级冲突、路径/分支保护和模型失败。soft 不能标成硬拦截，也不能当成人工复核已完成。
- 展示“已记录调用中的 diff 检测状态”，限定分母；不显示无法证实的“全部 Agent 调用合规率”。审计启动前、其他版本/固定 commit 副本、未接入进程和绕过 CLI 的行为均不可观测。resolve 与 check 没有可靠关联标识时不自动配对。
- 历史详情使用调用当时的规则摘要和命中快照，不拿当前规则覆盖旧结果；不保存 API key、token、完整提示词或原始 diff。
- 按知识库归档，统一存入独立于规则 YAML 扫描目录的本地审计位置，支持测试注入存储位置。跨进程安全追加，读取时容忍末尾中断记录，暴露损坏/写入失败状态，不静默丢失记录。既有 kernel JSON v2、stdout 和退出码保持兼容，审计错误通过独立诊断路径报告。

## 实时性与规则一致性

页面每两秒轮询轻量摘要，只有版本变化才重载规则或调用增量。记录列表分页，不在每次轮询读取全部日志。失联保留最后一次数据并明确标记过期。

外部修改 YAML 后重新加载及 validate；无效时展示错误，不能把旧缓存标成最新有效。各次检测绑定不可变规则快照。保存、批准与检测之间明确串行边界，避免混用新旧规则。

## 与内置 Agent 的关系

本轮将 Standardizer 接到 chat/serve 的编辑 preview 与实际写入之间：使用该请求明确上下文和同一规则快照对拟写入 diff 检测，硬违规阻止写入，soft 随编辑结果返回并写入审计。默认 normal；已有 test/dev 使用限制继续适用，不从请求文件名推断模式。检查后若代码基线或规则版本变化，拒绝过期预览并要求重新生成，不能复用旧检查结果写入。

询问请求标记 diff 检测不适用，分别记录实际发生的规则校验与裁决。请求及其模型子调用通过 request ID 关联，模型调用只记录阶段、结果和可用用量，不保存提示词或凭据。undo/discard 记录独立恢复事务，展示原有路径、分支与冲突检查结果，明确标识其恢复性质及未执行的检测，不能伪装成新编辑检查通过。

聊天模式规则更新必须在下一个请求开始前重新加载校验，并固定到该请求，避免 dashboard 保存与进行中编辑互相改变上下文。新增检查通过可注入边界接到编辑模块，避免将 CLI 或 HTTP 依赖倒灌进 agent-runtime。

外部 Agent 的整个对话和任意工具调用同样不可从 CLI 推断。未来需统一调用入口或显式 run ID 的集成协议；本轮保留现有项目接入协议 v2，不虚构关联。

## API 与安全边界

新增 dashboard 专用接口，不改变 kernel JSON v2。只监听 127.0.0.1，生成每次启动的 token；所有读取数据和写入 API 要求 token，写入仅允许 POST，校验同源请求，禁止跨站访问。只操作启动时选定的知识库，不接受任意绝对文件写入。规则正文按文本呈现，避免 HTML 注入。

## 实现顺序与验收

先实现审计存储和确定性 CLI 埋点，再接入内置 Agent 的请求关联及写入前检查，实现规则读写服务与独立 HTTP 入口，最后完成 dashboard 界面及端到端验证。拆为内部模块，在同一次交付中完成规则管理、调用追踪和内置编辑拦截闭环。

- 原有 CLI fixtures、退出码和 kernel JSON Schema 保持兼容。
- 覆盖检测通过、真实硬拦截、soft、dev、无效参数、规则冲突、加载失败、未完成及并发记录，不捏造历史数据。
- 规则编辑验证覆盖错误回滚、重新批准、防覆盖外部修改、源文件定位与路径约束。
- 内置编辑覆盖硬违规不写入、soft 可见、基线或规则过期、正常编辑及恢复事务；询问和失败请求不能被误记为 diff 检测通过。
- 真实浏览器验证搜索筛选、详情、裁决、编辑保存、拦截详情、刷新、失联提示、窄屏和键盘操作；写操作使用临时知识库，避免污染真实规则。
- 执行适用模块测试和既有知识库校验。报告实际测试结果和未覆盖入口，不把构建或静态检查描述为真机验证。
